# Систематическая отладка (по мотивам obra/superpowers)

**Правило: исправление — только после найденной корневой причины.**
Исправить симптом = провал: поломка вернётся, плюс появится новая.

Применяется к любой поломке: ошибка в работающей системе, упавший тест, странное поведение, падение
сборки или выкладки. Простая поломка — процесс тот же, просто быстрый (2 минуты).

## Фазы (по порядку, не перескакивать)

### 1. Корневая причина
- **Прочитать ошибку целиком** — текст, номер строки, код ошибки. Там часто готовый ответ.
- **Воспроизвести стабильно** — какие шаги вызывают? Не воспроизводится → собирать данные, не гадать.
- **Что менялось?** — `git log` и изменения за последние дни, новые зависимости, переменные окружения.
- **Система из нескольких звеньев** (сообщение → обработчик → база; бот → внешний сервис → фоновая
  задача): добавить запись в журнал на КАЖДОЙ границе (что вошло / что вышло) и одним прогоном увидеть,
  ГДЕ именно ломается. Только потом копать это звено. (Пример: ошибка в фоне не видна — запись
  на границе покажет её за один прогон.)
- **Поломка в браузере или на телефоне**: не чинить вслепую — сначала найти
  симптом по лестнице источников: MDN → caniuse (вкладка Known issues) → багтрекеры браузеров →
  GitHub issues популярных библиотек (там уже наступили на эти грабли). Если приходится скриптом
  ОТМЕНЯТЬ поведение браузера — подход неверный: перестроить так, чтобы браузеру нечего было отменять.
  Эмулятор зелёный ≠ починено: последняя проверка — на настоящем устройстве.

### 2. Сравнение с работающим
- Найти похожее работающее место в этом же проекте. Выписать ВСЕ отличия от сломанного, даже
  «это не может влиять».

### 3. Гипотеза → минимальная проверка
- Одна гипотеза, вслух: «думаю, причина X, потому что Y».
- ОДНА минимальная правка для проверки. Не сработало → новая гипотеза, НЕ наваливать второе
  исправление поверх первого.

### 4. Исправление
- Сначала воспроизводящий тест или скрипт (он должен упасть ДО исправления).
- Одно исправление = одна причина. Без «заодно причешу».
- Проверка — делом (запуск, тест), только потом сохранение.

## 3 неудачных исправления подряд = СТОП
Это не «нужно четвёртое», это **проблема в подходе**. Остановиться и сказать человеку на пальцах:
«чинил трижды, каждый раз вылезает в новом месте — похоже, сам подход X неверный, предлагаю Y» — и обсудить.

## Таблица отговорок (поймал себя на этом → вернуться в фазу 1)

| Отговорка | Реальность |
|---|---|
| «Быстро поправлю сейчас, разберусь потом» | Первое исправление задаёт шаблон. Разобраться = быстрее. |
| «Наверное, дело в X, попробую поменять» | «Наверное» — это не причина. Проверь. |
| «Поменяю сразу несколько мест и прогоню» | Не поймёшь, что помогло. И появятся новые поломки. |
| «Поломка простая, процесс не нужен» | У простых поломок тоже есть причина. Процесс займёт 2 минуты. |
| «Срочно, некогда разбираться» | Гадание в среднем дольше: 2–3 часа тыканья против 20 минут системно. |
| «Ещё одна попытка» (после 2+ неудач) | 3+ провала = вопрос к подходу, не к исправлению. |
